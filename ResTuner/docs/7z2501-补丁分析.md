## 0. 一句话结论

**这两个文件的"界面改造"100% 是 PE 资源（Resource）层面的替换，没有任何代码补丁。**
7zFM.exe 换的是工具栏位图（RT_BITMAP），7z.dll 换的是文件类型图标（RT_ICON + RT_GROUP_ICON）。
因此"新版本一键改造"在技术上是**完全可行**的，本质是一个**PE 资源重写器 + 规则引擎**，
但真正的工作量与风险点集中在 **.rsrc 节区重建**（7z.dll 需要塞进 216 个图标，节区膨胀 1.5 MB）。

## 2. 7zFM.exe：只改了 4 个头部字段 + .rsrc

### 2.1 非资源字节差异：**总共只有 4 处 / 8 字节**

| 偏移 | 含义 | 原版 | 补丁 |
|---|---|---|---|
| `0x119` | `SizeOfInitializedData` | `0x57600` | `0x56200` (−136) |
| `0x194` | 数据目录 `RESOURCE.Size` | `0xCD60` | `0xCCD8` (−136) |
| `0x2A8` | 节表 `.rsrc.VirtualSize` | `52576` | `52440` (−136) |
| `0x150` | `CheckSum` | `0x00000000` | `0x000F4820` |

其余 35,763 字节差异**全部落在 `.rsrc` 节区内部**。
`.text` / `.rdata` / `.data` / `.pdata` / `.reloc` 的原始字节**逐字节完全一致**，
所有节区的 RVA、RawPointer、RawSize 都不变 → **没有任何节区搬迁**。

### 2.2 资源清单：88 项，键集合完全不变；16 项内容变化

| 资源类型 | 数量 | 变化 |
|---|---|---|
| RT_BITMAP | 15 | **14 项被替换**（ID 190 未动） |
| RT_GROUP_ICON | 2 | 1 项被改（仅宽高字段，见缺陷 ①） |
| RT_ICON | 4 | 不变 |
| RT_VERSION | 1 | 4 字节被"重编译"（见缺陷 ②） |
| RT_DIALOG / RT_MENU / RT_STRING / RT_ACCELERATOR / RT_MANIFEST | 20/1/43/1/1 | 完全不变 |

### 2.3 工具栏位图 ID ↔ 素材映射（已用内容哈希逐一验证）

| 资源 ID | 尺寸/位深 | 对应素材 |
|---|---|---|
| 100 / 150 | 48×36 / 24×24, 4bpp | `toolbar\*\Add.bmp` |
| 101 / 151 | 同上 | `Extract.bmp` |
| 102 / 152 | 同上 | `Test.bmp` |
| 103 / 153 | 同上 | `Copy.bmp` |
| 104 / 154 | 同上 | `Move.bmp` |
| 105 / 155 | 同上 | `Delete.bmp` |
| 106 / 156 | 同上 | `Info.bmp` |
| 190 | 13×13, 1bpp, 100 B | 未替换（与 `7-zip.dll` 里的同名位图相同） |

写入内容 = `.bmp` 文件去掉 14 字节 `BITMAPFILEHEADER` 后的原样字节。
素材与目标位深/调色板完全一致（4bpp + 16 色，`biSizeImage` 均等），因此尺寸天然相等：
48×36 → 968 B，24×24 → 392 B。

> 结论：这一部**本可以原地覆盖，不需要重建 .rsrc**。现有补丁却整段重建了 .rsrc，
> 导致 9543 处、35,763 字节无谓变化（资源树和资源数据被重新布局）。

`.text` / `.rdata` / `.data` / `.pdata` 逐字节不变 → 只动了资源。

### 3.2 资源变更

- **删除** 旧 RT_ICON 1–54（每个格式只有 32×32 / 16×16 两个 8bpp 图标）

- **重建** 全部 27 个 RT_GROUP_ICON（8 项/组），组名是字符串 `"0"`…`"26"`
- RT_STRING（类型↔索引对照表）**未变**
- RT_VERSION 4 字节被重编译（同缺陷 ②）

## 4. 现有补丁的两个缺陷（建议不要复刻）

### 缺陷 ① `7zFM.exe` 的 GROUP_ICON #100 宽高被写坏

```
原版 00 00 | 01 00 | 01 00 | 6e 3f ...   ← 110×63
补丁 00 00 | 01 00 | 01 00 | 6e 6e ...   ← 110×110（高度被写成了宽度）
```
实际 RT_ICON #4 未变（仍是 110×63，9128 B）。
Windows 加载图标时以 RT_ICON 内部头为准，所以看不出问题，但这是明确的写 entry 逻辑错误
（很可能把 `biWidth` 当成了 `bHeight`，或 width/height 都取了 width）。

### 缺陷 ② RT_VERSION 被"重新编译"，4 个字节被改动

```
off 0x060: 01 → 00        （容器块 wType 被写成 0）
off 0x084: 01 → 00
off 0x092: 'b' → 'B'      （语言代码 040904b0 → 040904B0 被大写化）
off 0x280: 01 → 00
```
无任何品牌/描述字符串改动，纯属生成工具（特征与 Resource Hacker 的"重新编译全部资源"一致）
的副作用。我们自己的工具应当**未被改动的资源一律原样保留**。

### 缺陷 ③（附带）`7z.dll` 的 GROUP_ICON #4（arj）残留了 2 个旧图标

```
group "4" 共 10 项：
  32×32 8bpp  id=11   ← 旧图标残留
  16×16 8bpp  id=12   ← 旧图标残留
  256/64/48/40/32/24/20/16 32bpp  id=89..96  ← 新图标
```
旧 RT_ICON 1–54 本该全删，却漏了 11、12。后果：`.arj` 图标在 32×32/16×16 这两个尺寸上
存在 **8bpp 与 32bpp 两份重复项，且旧项排在前面**，Windows 的选择策略可能挑中 8bpp 那份，
视觉上"只有 .arj 图标是糊的"。

## 5. 可行性评估

### 5.1 可以做的部分（高置信）

| 能力 | 依据 | 难度 |
|---|---|---|
| 用素材替换 7zFM 的 14 个工具栏位图 | 尺寸天然相等，可原地覆盖 | 低 |
| 用 `.ico` 重建 7z.dll 的 27 个图标组 + 216 个 RT_ICON | 索引映射来自目标文件自身 | 中 |
| .rsrc 节区重建 + 头部字段维护 | 已有一份可用的正确参考实现（本补丁） | **高** |
| 版本自适应（新版本免手工改映射） | RT_STRING 自描述 + ID 稳定 | 中 |

### 5.2 主要风险

1. **.rsrc 重建器的正确性**（核心风险）
   要正确生成三层资源目录树 + 数据项 + 4/8 字节对齐，并同步维护
   `VirtualSize / SizeOfImage / SizeOfInitializedData / RESOURCE.Size / BASERELOC.RVA / CheckSum`。
   写错不会立刻崩，可能在特定场景（如 shell 图标提取、静态链接的加载器）才暴露。
2. **数字签名**：官方后续版本若带 Authenticode 签名，改资源后签名必然失效。
   当前 25.01 这份原版**无签名、CheckSum=0**（所以现在没这个问题），但未来不保证。
   工具需要能检测并（可选）剥离签名表 + 重算校验和，并明确告知用户。
3. **权限与文件占用**：`C:\Program Files\7-Zip` 需要管理员权限；7zFM/资源管理器加载着
   7z.dll 时文件被锁 → 需要"检测占用 → 提示关闭 → 重试"的流程。
4. **视觉生效延迟**：Explorer 图标缓存不会自动刷新，改完看起来"没变"。
   需要附带"刷新图标缓存 / 重启 explorer"的动作（`ie4uinit.exe -show` 等）。
5. **版本漂移的兜底**：若将来工具栏位图 ID 变了、或新增格式没有对应 `.ico`，
   必须"能做的做、不能做的明确报告并跳过"，而不是静默半成品。

### 5.3 两条实现路线

| | A. 自研 PE/资源重写（Python） | B. Win32 `BeginUpdateResource/UpdateResource/EndUpdateResource` |
|---|---|---|
| 原理 | 自己解析并重排 .rsrc | 交给 Windows 资源 API 重写 |
| 可靠性 | 需要严谨实现 + 充分测试 | 系统级，重排/对齐/校验和都由系统处理 |
| 可控性 | 完全可控，可做"最小改动"与精细自检 | 只能整体重写，无法约束布局 |
| 可测试性 | 好（纯数据，可单测/CI） | 差（只能在 Windows 跑，需真文件） |
| 平台 | 跨平台 | 仅 Windows |
| 依赖 | 无 | 需提权场景下的 API 调用 |

建议：**以 A 为主**，并把 B 作为"交叉验证工具"（用它生成一份输出，再和 A 的输出做资源级比对），
而不是作为产品实现。

## 6. 建议的产品形态（草案，待你确认）

```
                  ┌─────────────────────────────────────────┐
   官方新版发布 →  │ 1. 定位目标（已安装目录 / 解压目录 / 安装包）│
                  │ 2. 识别版本（RT_VERSION FileVersion）        │
                  │ 3. 备份（.bak 或 时间戳备份目录）             │
                  │ 4. 执行规则：                                │
                  │    7z.dll   → 文件类型图标（按 RT_STRING 映射）│
                  │    7zFM.exe → 工具栏位图（按固定 ID 表）      │
                  │ 5. 写回（等尺寸原地覆盖；变尺寸重建 .rsrc）    │
                  │ 6. 自检（重新解析 + 资源集比对 + 冒烟运行）    │
                  │ 7. 刷新图标缓存 → 报告                       │
                  └─────────────────────────────────────────┘
```

核心模块：

| 模块 | 职责 |
|---|---|
| `pe.py` | PE 头/节表/数据目录 读写 |
| `rsrc.py` | 资源树解析；**.rsrc 重建器**（含对齐、数据项、头部同步） |
| `icon.py` | `.ico` 解析 → `RT_ICON` 列表 + 正确的 `GRPICONDIR`（修缺陷①） |
| `bmp.py` | `.bmp` 去 `BITMAPFILEHEADER`；位深/调色板兼容性校验 |
| `rules.py` | 规则引擎（manifest 驱动：哪个文件、哪类资源、用什么素材） |
| `verify.py` | 输出自检（可解析、资源集符合预期、图标可解码、可选启动 7zFM） |
| `backup.py` | 备份/恢复/幂等（已打补丁检测） |
| `cli.py` / `gui.py` | 入口 |

### 验收标准（建议）

1. 用官方 25.01 原版跑一遍，产出与现有 `patches\7z2501-x64-patch` **资源级完全等价**
   （键集合、每个资源内容的 SHA-1 一致），仅允许修掉缺陷①②③。
2. 产出文件能被 `dumpbin /headers` 解析、`7z.exe i` 正常列出格式、7zFM 能启动、图标正确显示。
3. 二次运行应识别"已打过补丁"并拒绝/提示，而不是叠加。
4. 错误输入（32 位文件、旧版本、非 7-Zip PE、损坏文件）应明确报错而不是产出坏文件。
